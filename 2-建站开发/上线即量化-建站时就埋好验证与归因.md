# 上线即量化：建站时就埋好验证与归因

> 一步笔记 / 第 2 步·建站开发
> 主源：赫兹《卖空气验证需求》(015)、《需求的痛点决定了转化率》(029)；方法骨架见项目 skill `mvp-validation`。
> 适用于：任何要验证付费意愿的站，不限平台、不限产品形态。

## 一句话原则

**自然流量不是验证信号，真实行动才是。** 所以建站配置阶段就要把「能改变下一步决策的事件」埋好，上线第一天就能按顺序闸门归因，而不是上线两周后才发现只能凭感觉说「结果一般」。

新手最常犯的错：盯着 PV / 访客数 / 排名纠结做不做。这些是噪声（还混着扫描器和爬虫）。真正决定 build / abandon / maintain 的是**合资格人接触页面后的行动序列**：看到 → 输入 → 看结果 → 询价 → 点购买 → 付款。

## 为什么建站时就要做，不是验证时再补

验证期一上线就开始有真人来访。如果埋点没装、触达没记，你永远只能事后凭印象复盘，归因不准 → 要么误判放弃一个好方向，要么在错切口上无限优化。这些是**零成本建站动作**，属于配置不是功能，不该拖到「先看看有没有流量再说」。

## 1. 上线前必写：验证合同（每站一份，写死防拖延）

每开一个验证站，先在项目里建一份验证合同，字段固定：

```text
方向名：
本轮截止时间：        上线后 7–14 天，到期必须决定 build / revise / reject
现金预算上限：        域名 + 前端 + 小额广告
合资格访问上限：      如 50–100 个目标人群访问（不是 PV，是去重真人）
成功行动标准：        至少 3 人提交真实项目参数 + 至少 1 人点购买/愿预付
                      （「有人说感兴趣」「点赞」不算）
停止条件：            曝光不足先换流量；曝光够但无人行动则归因承接/价格/痛点
到期必须做的决定：    build 最小可用 MVP / revise 承接或切口 / reject 方向
```

失败时不能用「再优化一下页面」代替结论。合同到期就必须做决定。

## 2. 建站时就装好的埋点（通用事件清单，不绑定产品）

只收集**会改变决策的事件**，不装花里胡哨的热图/SEO 建议当成功信号。按漏斗从浅到深，每个站都装这 7 个：

| # | 事件 | 判断什么 | 缺它会怎样 |
|---|---|---|---|
| 1 | `page_view`（到达） | 有没有曝光 | 不知道流量闸过没过 |
| 2 | `start_input`（开始输入） | 承诺有没有被理解 | 分不清「没看到」和「看不懂」 |
| 3 | `complete_input`（完成输入） | 输入摩擦 | 不知道表单/示例卡不卡人 |
| 4 | `view_result`（查看结果） | 结果有没有价值 | 不知道给了价值后掉不掉 |
| 5 | `click_buy`（点击购买） | 价格/付费时刻是否被接受 | 最关键分水岭，没埋等于瞎 |
| 6 | `checkout`（进结算） | 真实购买意图 | 区分「手滑」和「真要付」 |
| 7 | `pay`（付款成功） | 商业证据 | 最强信号 |

通用实现要点（不限技术栈）：

- **去重真人**：埋点前先排除自己 IP、已知扫描器 UA、订阅客户端轮询路径（`.env`/`phpinfo`/`mihomo.yaml` 等）。否则扫描器会把你的数据污染成「日访问上千」。
- **区分「人」和「请求」**：成功标准按「去重真人访问」算，不按 PV 算。一个真人翻 5 页 = 5 个 PV，不是 5 个潜在客户。
- **示例结果可看不可挡**：用户无需注册、无需付费就能看到示例输入与结果卡；墙放在更深的 Pro 动作上，不挡漏斗上层。
- **价格与 CTA 真实**：放一个真实价格和一个购买入口（不是「Coming soon」），价格是待测假设。赫兹 015：价格不能太低，否则熟人出于鼓励支持，不反映真实付费意愿。

## 3. 每渠道触达记录卡（通用，不限 Reddit）

任何主动触达（Reddit / X / 小红书 / Discord / 邮件 / 地推 / 广告）每次都记，字段固定：

```text
# | 日期 | 平台/社区 | 对象 | 对象资格 | 动作类型 | 消息摘要 | 回应 | 行动结果 | 信号等级
```

- **对象资格**：合资格 / 待核 / 不合资格。合资格 = 角色匹配 + 场景匹配 + 判断资格 + 沟通正当性，缺一不可。
- **动作类型**：公开回复 / 私信（征得许可后）/ 访谈 / 展示页面。
- **行动结果**：输入 / 询价 / 预订 / 付款 / 无。
- **信号等级**：弱（点赞、口头好评）/ 中（留联系方式、接受访谈）/ 强（提交真实项目、询价、订金、付款）。

没有这张卡，你只能说「结果一般」；有这张卡，模型才能按闸门归因。触达上限达到就停，不追发；渠道持续被过滤就换渠道，**渠道失败 ≠ 需求不存在**。

## 4. 顺序闸门归因：从量化数据直接判 build / abandon / maintain

按顺序看，**任何前置项失败都不能被后面的指标抵消**：

| 量化结果 | 归因闸 | 结论方向 | 唯一下一步 |
|---|---|---|---|
| 合资格触达量 < 上限，到站去重真人个位数 | **流量闸** | 不放弃 | 换触达姿势/渠道/账号，与产品无关 |
| 曝光够（合资格人到站 ≥ 上限）但 `start_input` ≈ 0 | **承接闸** | revise 页面 | 改承诺/示例/文案，不弃方向 |
| 有 `complete_input` 但 `click_buy` ≈ 0 | **价值/价格闸** | revise 切口或价格 | 改价格、改痛点切口、改付费时刻 |
| 有 `click_buy` / `checkout` 但 `pay` ≈ 0 | **支付/信任闸** | revise 支付路径 | 查信任、退款说明、支付摩擦 |
| 出现询价 / 订金 / 付款（强信号） | **商业证据** | **build** | 做最小可用 MVP，不急扩量 |
| 触达足够多合资格人，三层行动全零且已换过渠道/页面/价格 | **方向级反证** | **reject** | 记失败闸门回 Seed Pool |

### build / maintain / abandon 的判定线

- **build**：出现强行动信号（询价 / 订金 / 付款）。信号量小也没关系，先做最小可用 MVP，再扩量。
- **maintain**：有中信号（留联系方式、接受访谈、提交真实项目）但还没付款。保持触达、小步改承接，不投入重开发，等强信号。
- **abandon（reject）**：触达了足够多合资格人（达到合同上限）、且已至少换过一轮渠道/页面/价格，三层行动（输入/询价/付款）全零。这是唯一能判方向死刑的条件——**「自然流量为零」不在此列**。

> 关键护栏：自然流量为零、Reddit 触达结果一般、熟人没反馈——这些单独都不构成 abandon。只有「合资格人足够多地接触方案后仍不行动」才是方向级反证。

## 5. 模型读取协议（Agent 怎么用这些数做判断）

当用户问「这个 MVP 该做、放弃还是维护」时，Agent 按这个顺序读：

1. **先查验证合同**：有没有写死截止时间和成功标准。没有 → 第一步是补合同，不是分析数据。
2. **读触达记录卡**：合资格触达了多少人？没记录 → 第一步是补记录卡，归因无从谈起。
3. **读埋点漏斗**：7 个事件各多少人？先把扫描器/订阅轮询/自己 IP 排除，只看去重真人。
4. **按顺序闸门归因**：找到第一个失败的闸，给唯一下一步。不要用后面的指标补偿前面的失败。
5. **对照判定线给结论**：build / maintain / abandon，附理由和需要的下一个动作。
6. **不越权**：build/abandon 是用户决定，Agent 给推荐 + 理由。每轮最多补一次关键未知（通常是「合资格触达了多少人、行动分几层」）后交还用户。
