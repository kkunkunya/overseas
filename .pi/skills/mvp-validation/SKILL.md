# mvp-validation

用最小、诚实的承接物测试一个会改变决定的行动信号，不把验证页扩成完整产品。

```text
付费假设 → 验证合同 → 最小兑现 → 合资格触达 → 归因 → build / revise / reject
```

## 1. 写验证合同

```text
若 {人群} 在 {高代价场景} 看见 {输入→具体结果} 并面对 {真实价格}，
则会 {提交真实任务 / 预订 / 询价 / 付款}。
```

设定本轮截止时间、可接受成本、合资格流量或触达上限、什么行动支持假设、什么结果触发改承诺/换流量/停止。目标是推翻最高风险，不是累积“感兴趣”。

## 2. 展示完整工作，最小兑现关键一步

让用户看懂：谁在什么时刻交什么输入，得到什么可行动结果，因而省什么时间、风险或成本。

- 首屏给结果承诺与真实样例；
- 用最短链路兑现决定购买信心的核心一步，未实现部分清楚标计划；
- 放一个明确价格、购买/预订路径和提交真实任务入口；
- 记录到达、开始、完成、结果有用、提交、购买点击、checkout 与付款；
- 说明交付边界、数据处理、联系方式和退款/取消条件。

需要逐项检查时读 [最小验证页清单](assets/landing-page-checklist.md)。账号、后台、自动化和多档套餐只在重复行动证明必要时补。

## 3. 合规地取得行动

选择目标人群已经出现、规则允许的渠道。触达前确认页面与事件记录能回收来源和行动；每次记录对象资格、上下文、来源、回应和后续动作。先在真实讨论中提供帮助，获许可后再邀请看页面或交流。

需要渠道边界与记录格式时读取 [社区触达](references/community-outreach.md) 和 [触达记录](assets/outreach-record.md)。对外发布、广告、收款或私聊先由用户授权。

## 4. 按最早失败环节决定

| 观察 | 优先检查 | 不能推出 |
|---|---|---|
| 合资格用户没看见 | 流量/触达入口 | 需求不存在 |
| 看见但不输入 | 承诺、信任或理解 | 产品一定无价值 |
| 输入/咨询但不购买 | 结果价值、价格或付费时刻 | 已可规模化 |
| 重复使用、主动询价、订金或付款 | 商业信号 | SEO/分发已解决 |

到期后选择 `build / revise / reject`。如果继续美化页面、加功能或收集泛泛反馈不能改变决定，执行结论。

**完成判据**：验证合同、真实价格、最小兑现与事件记录已就绪；结果能归到最早失败环节，并得出唯一下一步。
