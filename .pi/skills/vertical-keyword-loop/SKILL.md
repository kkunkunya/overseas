# vertical-keyword-loop

关键词不是产品方向。它先暴露用户正在找的入口，再回到用户为何需要结果、现在如何凑合，以及我们能交付哪一个更好的结果。

```text
用户任务假设 → 词群 → SERP 与竞品 → 当前替代 → 可交付产品结果 → 商业行动 → 灯色
```

## 1. 从任务找词

先写 `谁 × 场合 × 要完成什么 × 现在如何凑合`，再收集 5–15 条英文搜索短语。词只按用户所处阶段分组：他是在找基础工具、理解已有结果、比较方案，还是寻找深度交付。不要把词按量从高到低直接列进报告。

优先寻找旧需求里还没被顺畅承接的一步。该步必须能写成一句产品承诺：用户交什么输入，马上拿走什么结果，为什么现有替代还给不了。

## 2. 用词和竞品找产品缺口

需要实时数据时先交 `treg-research`，并说明本轮要改变的产品判断。每个准备进短名单的词群只查足以回答下面四件事的证据：

1. **用户在找哪一步。** 主词和少量修饰词的 SERP，前排页面让用户算、读、比较、购买还是预约什么。
2. **现有替代漏了哪一步。** 打开 3–5 个前排结果，顺着输入、结果、样例、价格和 CTA 走一遍；正式竞品样本优先已有「目标用户 → 可用结果 → 支付入口 → 成交或收入线索」闭环的站点。只有流量、融资或功能展示的站点可说明需求或 SERP，不能单独说明生意成立；记录用户得到什么、还得自己补什么。
3. **我们能交付什么不同结果。** 不把“更多内容、更好看、AI”写成差异；写用户的输入、可拿走的结果和边界。
4. **这个结果是否有商业动作。** 看价格页、人工替代、升级时刻或用户原话。没有真实付费前，只能称为待验证的购买单位。

数据只保留会改变上述四个判断的一两项。报告里不解释指标或术语；在证据旁直接写它推动的产品选择和仍缺的验证。

## 3. 把词群收成产品实验

最多保留 3 个词群。每项交付只写：用户任务、当前替代、未被承接的一步、我们能交付的结果、最小商业行动、未知项与灯色。

对准备建议 `go` 的一个切口，用 1–3 个实操演示、社区原话或等价一手材料还原：

```text
触发 → 输入 → 当前替代的步骤 → 卡点 → 用户想拿走的结果 → 能否为这个结果行动或付费
```

需要固定记录时读 [场景卡](assets/scene-card.md)。原型应验证产品结果和行动，不验证一张关键词表是否好看。

## 4. 灯色与交接

| 结论 | 含义 | 交接 |
|---|---|---|
| `go` | 用户任务、现有替代缺口、可交付结果以及搜索、竞争与变现线索同时有证据 | `seo-site-blueprint`，规划可用 MVP、SEO/GEO 最小包与首版范围。 |
| `watch` | 缺一项会改变产品判断的证据 | 写唯一复查条件 |
| `narrow` | 需求存在，但只在更窄的人群、触发时刻、结果或页型成立 | 收窄后重新取证 |
| `reject` | 用户不需要额外结果，或没有可交付、可变现的缺口 | 记录最早失败证据，回种子池 |

用户拍板最终结论。

**完成判据**：短名单不超过 3 个；每项都说清用户任务、当前替代、产品结果、变现线索、未知项与灯色；`go` 有场景说明和一句可兑现的窄承诺，并交给 `seo-site-blueprint`。
