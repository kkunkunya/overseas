# direction-validator

从外部信号回到客户正在完成的任务，再判断这个任务应该由搜索资产、一次性产品还是重复工作流承接。

```text
外部信号 → 谁在何时要完成什么 → 当前替代为何不够 → 可交付结果 → 付费时刻 → 最小反证
```

## 1. 选择路线

先从用户原话、真实讨论、现有替代和触发时刻写 `谁 × 什么场景 × 要完成什么任务`。接着写用户此刻交得出的输入，以及用户能拿走的可观察结果。产品形态由这两件事决定：

| 任务性质 | 优先承接 | 需要先拿到的证据 |
|---|---|---|
| 用户主动搜索一次性问题，独立页面能让他完成结果或理解下一步 | 搜索入口 + 小产品 | SERP 页型、当前替代、结果能否兑现、后续付费或行动。 |
| 用户反复完成多步骤工作，涉及状态、协作、集成或高风险交接 | Workflow SaaS | 完整流程、反复频率、切换成本、谁为损失和结果买单。 |
| 免费一次结果之后，确实有人继续交出后续工作 | 混合式楔子 | 免费结果完成行为，以及用户主动提出的保存、批量、深度交付或持续需求。 |

词和流量只负责找到入口，不能代替“用户为什么需要这个结果”的证据。

## 2. 测最高风险，不用研究代替决定

列出 3–5 条可被推翻的假设，为每条标商业影响与证据不确定性。优先测试最高的一条：

```text
若对 {人群} 在 {场景} 提供 {输入→结果 / 价格 / 触达}，
则会出现 {可观察行动}。
```

先设本轮范围：最多深查几个候选、什么行动算支持、什么结果触发 `watch/narrow/reject`。新资料不能改变结论时停止继续搜集。

## 3. 取得路线对应的最小证据

先让外部信号落到真实任务。关键词、竞品页、评论、人工服务和访谈只记录三件事：用户在什么时刻想完成什么、现在怎样凑合、哪一个结果值得换产品。

Workflow SaaS 或混合式楔子用 [工作流证据卡](assets/workflow-evidence-card.md) 记录：

```text
触发 → 输入 → 当前完整步骤 → 输出/交接 → 当前替代与摩擦
→ 谁承担损失 → 谁买单、何时付费 → 最小反证
```

需要实时外部事实时先走 `treg-research`。从真实社区、评论、产品、人工服务或访谈取得原话与流程；每条线索保留时间、原话、场景和当前替代。需要登录态、版规或上下文时用用户 Chrome 真实核验。产品切口成立的标准是：当前替代漏掉了一步，而我们能交付那个结果；“更漂亮/更智能”没有单独的购买单位。

## 4. 灯色与交接

| 结论 | 条件 | 交接 |
|---|---|---|
| `go` | 客户任务、当前替代缺口、可交付结果与搜索/竞争/变现线索已清楚 | 搜索入口进入 `vertical-keyword-loop`；SEO 产品进入 `seo-site-blueprint`，做可用 MVP 并上线观察。 |
| `watch` | 缺一项关键证据 | 写唯一复查条件 |
| `narrow` | 只有更窄任务或交接被证实 | 保留它重新取证 |
| `reject` | 工作不具体、替代不痛、不可触达或无商业理由 | 记录最早失败证据 |

用户决定最终方向与对外动作。

**完成判据**：客户任务、当前替代、可交付结果、最高风险假设与唯一下一步已写清；搜索词、外部取证、页面建设和上线复盘分别交给对应 skill。
