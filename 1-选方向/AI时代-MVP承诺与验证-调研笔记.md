# AI 时代：MVP 承诺与需求验证

> 日期：2026-07-30  
> 问题：生成式 AI 使单点工具很容易复制时，卖空气验证是否还应只做一个极简 Landing Page？

## 结论

**保留“先验证、不要先建完整 SaaS”，但把验证物从静态概念页升级为 product-shaped MVP（像产品的最小可信证明）。**

MVP 的“最小”指最小可验证闭环，不指最少输入框。页面应让目标用户看见完整的 job outcome、一个可信的样例交付物和相邻任务如何连起来；其中只有决策关键的一步需要真的可用或以 concierge（人工交付）兑现。其余能力可以呈现为 roadmap，但必须标明状态。

不能从通用 AI 使用趋势直接推出某个细分产品值得收费。最终仍以用户是否带着真实工作进入、是否要求结果、是否愿意付费来判定。

## 已查的一手资料

1. **Anthropic, “Building effective agents”**（2024-12，持续维护）
   - https://www.anthropic.com/engineering/building-effective-agents
   - 原文基于与多支团队的实践，指出成功实现通常使用“simple, composable patterns”，并区分预定义代码路径的 workflow 与动态决策的 agent。
   - 可迁移结论：不要把“AI 能做很多事”误解为 MVP 必须做成大而全自主产品；先定义一个可组合、能交付结果的工作流闭环。

2. **OpenAI, “A practical guide to building agents”**（2025）
   - https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf
   - 官方实践指南聚焦：先判定 agent 是否适合该任务，再从单 agent / 工具 / guardrail 的最小架构起步，按任务复杂度扩展。
   - 可迁移结论：对用户可见的“完整承诺”与内部先实现多少自动化应分离；先以人工或窄自动化兑现高价值结果，再用真实重复任务决定自动化边界。

## 从资料与本项目得到的操作规则

### 1. 卖 outcome，不卖裸功能

用下面句式写首屏：

```text
For {谁} facing {高代价时刻},
{产品} takes {真实输入} and gives {可拿去行动的产物/决定},
so they can {避免损失 / 完成工作 / 获得收入}.
```

反例：`AI 自动报价`。

较强承诺：`把客户参考图变成可发送的报价、利润与确认素材，让定制卖家在接单前知道是否值得做。`

### 2. 页面画完整工作流，交付只兑现关键步

把候选能力按角色分三层，避免 feature soup：

| 层 | 页面如何呈现 | 本轮是否必须实现 |
|---|---|---|
| 核心 verdict / artifact | 样例输入 → 过程 → 具体输出，主 CTA 直达 | 是；可人工交付 |
| 相邻工作步骤 | workflow 图、示例卡、明确说明如何接上 | 仅在用户反复要求时实现 |
| 扩展 / 管理能力 | `Planned` 或 `Founding-member input` 标识 | 否；不暗示已可用 |

一个能力只有同时满足“同一用户、同一时刻、同一任务的下一步”才应进入页面；否则它是在制造假想的 I Love PDF，而不是聚焦的工作台。

### 3. 以可信展示抵抗“我直接问 AI”

页面至少放一种不可只靠文案理解的证据：

- 脱敏的真实样例报告 / 报价单 / 项目包；
- 交互式输入到结果的 demo；
- 人工核验 / 数据源 / 责任边界；
- 两个方案的比较和明确决策建议。

它要回答的是：`为什么这个结果比我自己 prompt 一次更可靠、更省事、可复用？`

### 4. 用付费动作验证，不用预约数量自我安慰

| 信号 | 证明什么 |
|---|---|
| 留邮箱 | 轻兴趣，不足以下结论 |
| 提交真实图片 / SKU / 客户需求 | 有正在发生的任务 |
| 接受人工交付、补充资料或追问下一步 | 愿意把产品放进工作流 |
| 点击真实 checkout、订金、预付款 | 付费意愿 |

本轮建议门槛：10–15 个合资格对象中，至少 3 个提交真实任务；人工交付后至少 2 个追问/复用；至少 1 个接受真实 $29 付款或订金路径。低于此标准时，按流量、承诺/信任、价值/价格分开归因。

## 对原 `mvp-validation` 的具体变更

原规则“做一页可丢弃 Landing Page，不做产品”过度容易被执行成“只放静态功能清单”。应改为：做一个可丢弃的 product-shaped MVP——Landing Page + 关键结果 demo 或 concierge 交付；展示完整的相邻工作流，但对未实现项诚实标注。页面复杂度不是目标，可信的 end-to-end promise 才是。
