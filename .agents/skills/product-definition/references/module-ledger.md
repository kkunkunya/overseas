# 模块账、收费设计、验证机制

## 模块账

每个模块一行，三栏都要有话说：

| 模块 | 省了用户什么麻烦 | 对留存的作用 | 对付费的作用 | 去留 |
|---|---|---|---|---|
| 名字 | 没它用户要自己做什么，一句话 | 会不会让他再回来；怎么回来（节点、提醒、新结果、积累的数据） | 是不是一个值得收费的结果节点；还是只是免费的铺垫 | 做 / 推后 / 砍 |

规则：

- **省的麻烦要具体**：「没它用户得手工比对两份表」可以；「体验更好」不行。
- **留存分三档**：强（用户会因它再来）、弱（来了更顺）、无。需求只在节点出现或一次性的产品，「再来」改看两件事：来年节点会不能再来，和它能不能带来新用户（被分享、被转介绍），栏里写清是哪一种。无也可以留，但不能是主推点所在的模块。
- **付费分三档**：是收费节点、是通往收费节点的必经路、与付费无关。全是「无关」且留存也是「无」的模块，砍。
- **三栏说不清的砍或推后**，写进「以后」栏并注明等什么证据再做，不悄悄塞进首版。
- 首版模块数以能把核心路径跑通为限；加功能前先问它落在哪一屏、挤掉了谁。

## 收费设计

| 要写清 | 怎么判 |
|---|---|
| 付费墙放哪 | 放在**用户最想拿到那个心理结果的一刻**（刚看到结果的价值、想拿走或继续），不放在 Aha 之前。能让用户先尝到一次结果的，Aha 免费、拿走或深入收费；文案说的是他拿到的心理结果，不是功能清单 |
| 订阅还是单次 | 看需求是否反复发生：一次性或会自然结束 → 单次/买断；每天每周都发生 → 订阅（承接选品的「持续帮助」判断） |
| 漏斗怎么走 | 进入 → Aha → 付费墙 → 付款 → 回访，每步写一个会被问到的数字（先留空标 `待测`）；谁付钱、谁用、谁传播若不是同一人，漏斗分开写 |
| 利润口径 | 单次收入 −（模型/API 成本 + 支付手续费 + 渠道费 + 人工）= 每单利润；订阅按月；成本项没来源写 `No data`，价格起点对照竞品价格页 |
| 旺季与加购 | 需求峰值在哪，平时靠什么撑；结果出来后还能加卖什么 |

价格数字注明「已核实 / 自报 / 估算」及来源，没有写 `No data`。

## 验证机制

目的：证明**用户心理是真的**，不是我们以为的。分上线前后写：

- **上线前**：小样本（5–10 个目标人群）看他们在 Aha 屏的反应和是否愿意走到付费墙；或做一个只有核心路径的假页/人工代做（concierge），看有人愿意交出材料、愿意付钱。
- **上线后**：体验后给点奖励（积分、额度）换一句反馈或一次分享，看谁愿意回头、愿意传播；看 Aha 到付费墙的流失点。数据口径和实验交 `product-growth-review`。
- 每条验证写：**要验的假设 / 做法 / 什么信号算成立 / 不成立就改哪一条**。信号写成可观察的行为，不写「用户喜欢」。
