## 一、整体逻辑判断

**结论：这套流程的骨架是对的，可以按它开工；不需要推倒重来。真正要动的是三处"锁"，它们会在正常工作中拒绝合理的下一步。**

用大白话讲：

1. **从"顾客要办什么事"一路走到"这一轮算不算数"，链条是连着的。** 25 个模块每一个都写了什么时候启动、要什么输入、做什么、交出什么、下一站是谁，没有断头路。JSON 里 25 条记录的 trigger/inputs/actions/output/check/next/source/tools 八个字段**无一缺失**（脚本核对）。HTML 的 25 张卡片标题、顺序、阶段与 JSON 完全一致，11 位小助手的名字与 mono 里 11 个 SKILL.md 一一对得上。这一层没有虚报。
2. **最值得表扬的是"不吹效果"这条底线守住了。** 从抓取 → 索引 → 展示 → 点击 → 用户完成任务 → 回访 → 付费 → 留存，每一格都被明确分开（`product-growth-review/SKILL.md:11`、`路线数据.json:496`），没有把"被收录"当成"有人用"，也没有把"AI 提到我"当成"AI 带来生意"（`geo-source-loop/SKILL.md:45`、`路线数据.json:214,218`）。数据状态分成"可用／待接入／不适用"，业务数据分成"真实／测试／未接通／零值"（`website-operations-loop.md:9-17,44`）——这两套区分是整套方法里最硬的部分，它直接挡住了"装了工具就当已验收"这个最常见的自欺。
3. **"准备工作能否提前"这一条整体做得比预期好。** 支付、域名、测量记账本、发布前快照都放在"现在准备"；邮件短信和多语言虽然在"条件出现"，但触发条件明确写了"现在就可以先设计／先规划，不需要已有联系人或第二市场数据"（`路线数据.json:290,350`），并且 `product-growth-review/SKILL.md:17,28` 和 `seo-site-blueprint/SKILL.md:19` 都专门开了"准备态"入口。这是个成熟的设计，不是常见的"等到那天再说"。
4. **但流程里埋了三处"只进不出"的锁**，它们单看每一条都有道理（防止你三天换一次方向），叠在一起会变成：**新证据出现时，系统没有合法路径让你提前收窄或止损**，而且**没有 Semrush 就无法开始选词**、**没有稳定排名就不许做 GEO 基线记录**。这三处是本轮最实的发现（见 F1/F2/F3）。
5. **一处事实需要更新**：整套 GEO 判断建立在"ChatGPT 用 Bing 索引、Perplexity 重 Bing、AI 不建自己的全网爬虫"这个机制断言上（`CONTEXT.md:175`）。查一手官方文档后，**这个断言现在不成立**：OpenAI 有自己的 `OAI-SearchBot` 用于 ChatGPT 搜索结果，Perplexity 有自己的 `PerplexityBot`，两家都自建抓取与索引。结论层面"先做好 SEO 是 GEO 的地基"仍然站得住（AI 大量引用仍与传统排名重叠），但**由这个机制推出的硬门槛（没排名就不许做 GEO）失去了依据**。

一句话给非专业读者：**路线图本身可以照着走，先把它的三把锁改成"带条件的门"，再把 GEO 那段的理由从"Bing 索引"改成"排名与被引用高度相关"。**

## 二、优先发现（8 项）

优先级：P1 = 会在正常使用中挡住合理工作；P2 = 会造成来回踢皮球或写不出东西；P3 = 体验/一致性。
类型：**逻辑缺陷** / **可选增强** / **产品实施项**。

### F1｜GEO 入场门比路线卡严格，且建立在已过时的机制断言上（P1，逻辑缺陷，置信度 高）

- 位置：`geo-source-loop/SKILL.md:17,25` ↔ `3-SEO获客/SEO-GEO全流程/路线数据.json:210`；机制断言在 `CONTEXT.md:175`
- 冲突点：路线卡说 GEO 的启动条件是"核心公开页面可用；准备研究目标用户会向 AI 问什么"；skill 的入场门却是"核心任务页在 Google/Bing 还没有**稳定露出**时**停止 GEO**"。两者不是一回事。
- 触发例子：网站刚上正式域名，GSC 显示"已抓取、未编入索引"。你照 HTML 路线图点开"让 AI 找到可核查的产品事实"，说"帮我先固定 10 个问题、记录今天 ChatGPT 和 Perplexity 怎么回答、来源是谁"。按 skill 的门，Agent 会回答"缺收录，停止 GEO"，把你踢回去。
- 但路线卡自己列的三个动作（固定问题/平台/日期并记录答案与来源、把被检索/被引用/被提及/被推荐分开、补可核查事实）**全都不需要你已经有排名**——第一条恰恰是上线前后就该做的基线快照，越早做越有对照价值。
- 事实核对（2026-09-07 查一手官方文档）：
  - OpenAI 开发者文档：`OAI-SearchBot` 的用途是"surface websites in search results in ChatGPT's search features"，`GPTBot`、`ChatGPT-User` 各有分工 → OpenAI 自建搜索抓取与索引，不是单纯用 Bing。（https://developers.openai.com/api/docs/bots）
  - Perplexity 文档：`PerplexityBot` "designed to surface and link websites in search results on Perplexity" → 自建爬虫与索引。（https://docs.perplexity.ai/guides/bots）
  - 因此 `CONTEXT.md:175` 的"ChatGPT 用 Bing 索引、Perplexity 重 Bing""AI 产品不建谷歌级全网爬虫，拿网页只有三条渠道"属于**过时/过强的机制断言**（观察事实）。"做好 SEO 基本等于做好 GEO 的地基"这个结论仍可保留，但要改成**相关性论证**（AI 引用与传统排名高度重叠、可抓取的初始 HTML 是共同前提），而不是**索引依赖论证**（推断）。
- 用户影响：上线初期最该做的 GEO 基线被拒绝；等有排名了才开始记录，就永远拿不到"改动前 vs 改动后"的对照，只剩一次性快照。
- 最小改进：把 `geo-source-loop` 的入场门拆成两档——**观察态**（只要核心页可访问即可做问题固定、答案与来源基线记录，禁止据此宣称效果）与**优化态**（要争取被引用/补第三方来源时，才要求核心页已在传统搜索有稳定露出）。同时把 `CONTEXT.md:175` 的机制句改写为可核对的现状 + 日期。

### F2｜"不退回选词 + 观察窗未满不归档 + narrow 需立项时已判断"三锁叠加，缺少新证据触发的提前止损通道（P1，逻辑缺陷，置信度 高）

- 位置：`seo-readiness-audit/SKILL.md:21,62`、`product-growth-review/SKILL.md:41,66,68`、`路线数据.json:501,502`、`vertical-keyword-loop/SKILL.md:67`
- 三条规则单独看都合理：不因几周没排名退回选词（对）；观察窗 8–12 周未满不归档（对，且已诚实标为"本仓启发式，不是科学定律"）；`narrow` 的条件是"**立项时**已判断前十差距扛不住"。
- 但第三条把"是否可以收窄"绑定在**立项当时的判断**上。触发例子：上线第 3 周你发现目标核心词的 SERP 页型全变成本地 pack 或即时咨询（不是你能做的形态），或竞品刚上线一个免费版把你的整个承诺覆盖了。这是**新证据**，不是"几周没排名"。按 `seo-readiness-audit/SKILL.md:62` 的字面规则，narrow 不成立（立项时没这么判断过）；按 `product-growth-review/SKILL.md:41` 也不能归档（窗口没满）。`recent-market-radar` 能出 `weaken`，但它自己声明"扫描本身不是新的生命周期阶段"（`recent-market-radar/SKILL.md:84`），只能把判断交回原阶段——而原阶段正被前两条锁住。
- 用户影响：明知该停的站，方法上没有合法的停法；人只能绕过方法自己拍板，久而久之整套流程失去权威。反过来也可能被"再等等"消耗掉 8–12 周的时间和维护精力。
- 最小改进：在 `product-growth-review` 的决定表加一行 `早停`：**当出现与"没排名"无关的决定性反证**（SERP 页型系统性不匹配、需求消失、平台/法律阻断、替代方案完整补齐缺口、单位经济为负）时，允许在观察窗内直接 `narrow` 或 `归档`，条件是写清反证证据、它为什么与短期排名波动无关、以及不再重开选词的范围。同步把 `seo-readiness-audit/SKILL.md:62` 的"立项时已判断"改为"立项时已判断**或**审计中取得新的页型/竞争证据"。

### F3｜选词证据硬绑 Semrush 人工导出，与同一套方法里的 treg 能力和"降级来源"条款自相矛盾（P1，逻辑缺陷，置信度 中高）

- 位置：`vertical-keyword-loop/SKILL.md:17,43`、`docs/adr/0016-...md:14` ↔ `CONTEXT.md:57,255`、`treg-research/SKILL.md:51`
- 矛盾三方：
  - `vertical-keyword-loop:17`："缺 Semrush 导出或截图时**停**……不编数字、**不改用 treg 顶上**"；ADR-0016 决策 1 同义。
  - `CONTEXT.md:57`："证据硬、阈值软：有通道就查；查不到就标缺失或写清**降级来源**"；`CONTEXT.md:255`："其他通道（Ahrefs 免费 KD、插件、DataForSEO）只在证据缺某一格时**作补数**，并标明来源"。
  - `treg-research/SKILL.md:51`：明确把"任务词的 keyword ideas、volume、SERP"列为可调用的取证能力。
- 触发例子：你手上有 Ahrefs 免费 KD 和 treg 的 DataForSEO 通道，但没有 Semrush 订阅，说"帮我把这个领域的参考站和核心词先做出来"。按 skill 的硬门，Agent 必须整轮停在"等你交 Semrush 图"，即使旁边就有可标注来源的合法降级通道。
- 用户影响：**选词是整条链的第一道闸**，闸卡在一个商业订阅上，等于整套方法对没有 Semrush 的时刻完全不可用；而这跟"禁止编造数字"这个真正要守的原则并不是同一件事。
- 最小改进：把规则从"必须是 Semrush"改成"**必须是可回溯、标明厂商与日期的实测数**"：Semrush 导出为**首选证据**；无 Semrush 时允许 Ahrefs/DataForSEO 等作**已标注的降级证据**，但短名单上每个词必须写清数字来自哪家、哪天、什么口径，且不得跨厂商精确横比（这条 `CONTEXT.md:39,49` 已经写好了）。顺带把 `CONTEXT.md:255` 与 ADR-0016 的口径统一，否则会一直互相打架。

### F4｜正式词池"只收 C"与 GEO 来源资产、主题集群、问题页的要求冲突（P2，逻辑缺陷，置信度 中）

- 位置：`vertical-keyword-loop/SKILL.md:55,60`、`docs/adr/0016-...md:16`、`CONTEXT.md:88,93` ↔ `CONTEXT.md:175,223`、`seo-site-blueprint/SKILL.md:39`、`路线数据.json:215`
- 冲突点：唯一有取证流程的正式词池明确**排除信息词**（"信息词、未核实意图、品牌首页词不进短名单"）。但方法的另一半反复要求做**主题集群**（核心任务页 → 子任务页 → 场景/问题页）、要求**自有教程/案例/说明页作为可被 AI 引用的来源资产**、要求 GEO"补能帮助用户的说明、示例和可核查事实"。这些几乎全是信息意图的内容。
- 触发例子：blueprint 让你写"场景/问题页"和 GEO 来源资产，你问"这些页对着哪些词写？"——3+15 里没有一个信息词，而且短名单已锁不许再扩。结果只能凭感觉编题目，或者干脆跳过，主题集群和 GEO 来源资产两块就都落空了。
- 用户影响：站的深度和 AI 可引用性都被词池规则截断；也容易让人误以为"信息内容没用"。
- 最小改进：保留"**正式池（决定做不做这个方向、开哪几张核心任务页）只收 C**"这个闸，另设一条**从属通道**："问题/说明页的选题来自已锁核心词的同一任务簇（用户真实提问、GSC 已有查询、AI 问题记录），不重开选词、不新增核心词、不为它们单独立项"。这样既不破坏 ADR-0016 的立项纪律，也让下游写得出东西。

### F6｜"专项方法"三项在生命周期路由表里没有行，总指路员路由不到（P2，一致性，置信度 中高）

- 位置：`路线数据.json:408-465`（commerce / service / team 三个模块，phase = 专项方法）↔ `ask-overseas/references/lifecycle-route.md:9-21`（13 行阶段表，无电商/代理服务/团队协作行）↔ `direction-validator/SKILL.md:13,35`

### F7｜分发与搜索所有权准备被整块推到"上线之后"，与"SEO 见效要 3–6 个月"的自身判断相冲突（P2，可选增强，置信度 中）

- 位置：`路线数据.json:186-190`（distribution，phase = 上线之后，trigger = "可访问的任务页已经能兑现承诺"）、`路线数据.json:165-171`（indexing，trigger = "正式域名已可访问"）↔ `CONTEXT.md:27,108`（长期稳定增长常 3–6 月+；"产品确定后，先默认检查 X/Threads/Instagram/Reddit 四个渠道的活跃度、具体社区、规则与 Top 帖形式"——这是**产品确定后**，不是上线后）
- 冲突点：知识库自己已经写明渠道调研属于"产品确定后"的准备动作，而且 SEO 本身要 3–6 个月才见效，冷启动分发是上线初期唯一能快速拿到真实反馈的通道。但路线图把整块分发（含只读的渠道规则调研、社区选点、素材与真实示例准备、目录机会台账建档）都放在"上线之后"。同理，GSC / Bing Webmaster 的站点所有权验证在买域名当天用 DNS 就能做完，路线上却排在 indexing（上线之后）。
- 触发例子：你现在处于"准备买域名上线"，问"我能不能先把要发的社区、规则和素材准备好"。按当前阶段划分，这不属于"现在准备"的 8 项，容易被推迟到上线后才开始，白白丢掉两三周。
- 用户影响：上线后最宝贵的头两周被用来做本可以提前做完的只读调研。

### F8｜HTML 里被首页点名为"当前下一步"的模块，在同阶段列表中排在最后一位（P3，产品实施项，置信度 高）
